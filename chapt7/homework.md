## 作业 1：硬件回环自测

**接线**：USB-TTL 插电脑 → 用杜邦线把模块的 **TX 和 RX 两个引脚短接**（自发自收）。

**跑之前**：
1. `ls /dev/ttyUSB* /dev/ttyACM*` 找到你的串口；
2. 若是 `Permission denied`：`sudo usermod -a -G dialout $USER`，然后**注销重新登录**；
3. 把端口路径传进去（默认 `/dev/ttyUSB0`）：

1. 去掉「长度字段」会怎样？去掉「CRC8」会怎样？
去掉长度字段：接收端就不知道载荷有多长，没法算 CRC 在哪个偏移、帧在哪结束。帧头 0xA5/帧尾 0x5A 虽然能定位「起止」，但有个致命问题——载荷数据里也可能恰好出现 0x5A（比如 float 的某个字节就是 0x5A）。没有长度字段，接收端遇到 0x5A 分不清「这是帧尾还是数据」，切帧就错了。而且协议要扩展时（不同命令载荷长度不同），没有长度就写死了，每加一种帧都得改代码。

去掉 CRC8：帧头、长度、帧尾只能保证「帧完整地到了」，不能保证「内容是对的」。串口线旁边一开电机，电磁干扰可能把 X 坐标 0.523 的某个比特翻成 -18.3，接收端毫无察觉，直接解包出一个错误坐标让下位机执行错误动作。CRC8 是唯一能发现「内容被篡改」的手段——它是数据完整性的保险。

一句话：帧头尾定位「帧在不在」，CRC8 验证「帧对不对」，两者管的事不一样。

2. 为什么解包必须 memcpy，不能指针强转？
两个硬理由，都是未定义行为/崩溃，不是风格问题：

对齐（非对齐访问）：rx_raw 是 uint8_t 数组，&rx_raw[3] 这个地址只保证 1 字节对齐；而 float 要求 4 字节对齐。强转成 PropTargetPayload* 再解引用 float，在 x86 上硬件会默默帮你补（能凑合跑），但在 ARM（STM32/树莓派）上非对齐访问直接 HardFault 死机。跨平台就埋了颗雷。

严格别名（strict aliasing）：C++ 编译器假设「不同类型的指针不指向同一块内存」。你用 float* 去读写一块实际是 uint8_t 数组的内存，编译器做优化时可能产生错误代码——即使没崩溃，结果也可能是错的。

memcpy 是「按字节搬」，不要求对齐、不违反别名规则，是编译器保证正确的唯一解包姿势。

3. 完整数据流：相机 → … → 下位机

相机（USB/工业相机）
   │   chapt6（CH9）：工业相机 SDK 驱动 + 多线程双缓冲取帧（不积压、不掉帧）
   ▼
一帧图像 cv::Mat

   │   chapt5（CH8）：图像处理找目标 + solvePnP 解算坐标（pnp）
   ▼
目标坐标 (x, y, z, yaw) + 置信度 confidence
   │   chapt7（CH10）：SerialPort 封包 [帧头+长度+命令+载荷+CRC8+帧尾]
   ▼
串口 /dev/ttyUSB0 ──TX──► 下位机（STM32）
   │   chapt7（CH10）：下位机按同一套协议解包 + CRC8 校验 → 执行动作
关键点在「标定 → PnP → 封包」这条链：标定（chapt5）是 PnP 的前提（没有内参 K 解不出坐标），PnP 解出的坐标（chapt5）是串口（chapt7）要传的内容。前面几章都是在给串口那一帧「准备正确的载荷」。
